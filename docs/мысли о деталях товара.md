> Аудит текущего состояния проекта и предлагаемый roadmap реализации buyer Product Detail.

Да. Я **изучил текущий `main` репозитория, документацию, миграции и фактическую структуру кода**, а не только существующий план. Последний актуальный коммит, который я вижу, — `21a6aa9` с завершённым buyer Home/Catalog UI. [Открыть репозиторий Shoppis](https://github.com/forantigravityyesser/Shoppis?utm_source=chatgpt.com)

# 2. Очень важный момент: у нас уже есть почти готовая "продавцовская" модель товара

Вот это особенно полезно.

В seller-части уже существует:

```text
Product
 ├── description
 ├── images
 ├── attributes
 ├── linkAttributes
 ├── variants
 │    └── inventory
 ├── price
 └── category
```

И уже есть:

`useProductDetail()`

и mapper:

`buildProductDetail()`

который собирает:

* товар;
* изображения;
* варианты;
* цены вариантов;
* остатки;
* характеристики;
* категорию.

То есть **доменную модель нам заново придумывать не надо**.

Но есть принципиальный нюанс:

### Мы НЕ должны просто подключить buyer DetailsView к seller `useProductDetail`.

Почему?

Потому что текущий seller repository делает:

```text
fetchCatalog(storeId)
    ↓
products
product_images
product_attributes
product_link_attributes
variants
inventory
```

То есть это **seller catalog read**, привязанный к внутреннему `storeId`.

Buyer Detail должен иметь другой boundary:

```text
public_id + product_id
        ↓
public storefront read
        ↓
только разрешённые buyer-данные
```

Особенно учитывая, что **RLS сейчас сознательно отложен**. Нельзя делать buyer Product Detail как набор прямых `.from('products')...` запросов и надеяться, что потом RLS всё закроет.

# 3. Самое важное архитектурное решение

Я предлагаю сделать отдельный read-model:

```text
StorefrontHome
StorefrontProductDetail
StorefrontReviews
StorefrontQuestions
```

а не пытаться расширять `StorefrontHome`.

Сейчас:

```ts
StorefrontHome {
  store
  categories
  products[]
}
```

И это правильно.

Product Detail должен жить отдельно:

```ts
StorefrontProductDetail {
  store
  product
  images
  attributes
  linkAttributes
  variants
  rating
  reviewsCount
  questionsCount
  relatedProducts
}
```

Причём **не тащить всё через Home**.

Это прямо соответствует уже зафиксированному правилу в `docs/13`:

> Home → Product ID → Product Detail → самостоятельная загрузка.

# 8. Reviews и Questions — отдельные nested routes

Вот здесь я предлагаю использовать возможности React Router, которые у нас уже есть.

Сейчас:

```text
/product/:id
```

Сделаем:

```text
/product/:id
/product/:id/reviews
/product/:id/questions
```

Причём:

```text
/product/:id
       │
       ├── reviews
       └── questions
```

через `<Outlet />`.

React Router как раз предназначает nested routes + `Outlet` для такого поведения: дочерний route рендерится внутри родительского layout. ([reactrouter.com][1])

Но визуально мы не будем делать обычную веб-страницу.

# 13. Варианты должны быть полностью серверными данными

Например:

```text
Size

[S]     [M]     [L]     [XL]
 5       0       7        2
```

UI получает:

```text
S → availableQuantity = 5
M → availableQuantity = 0
L → availableQuantity = 7
XL → availableQuantity = 2
```

и сам показывает:

```text
[S] [M disabled] [L] [XL]
```

Не надо вычислять наличие по общей сумме товара.

У нас inventory относится к **конкретному Variant**.

# 15. Add to Cart уже имеет хорошую основу

```text

productVariantId
quantity

```


Например:


→


И это полностью соответствует нашей бизнес-логике.

# 25. И вот что мне особенно нравится после аудита

**Нам не нужно ломать текущую архитектуру ради Product Detail.**

Наоборот, Product Detail отлично показывает, зачем мы вообще сделали нынешний Clean/Onion подход.

Сейчас уже есть:

```text
domain
   ↓
application
   ↓
ports
   ↓
infrastructure
   ↓
InsForge
```

и buyer Home уже доказал правильность read-model подхода:

```text
storefront_home_read()
        ↓
StorefrontRepository
        ↓
useStorefrontHome()
        ↓
HomeView
```

Теперь просто делаем второй read model:

```text
storefront_product_detail_read()
        ↓
StorefrontProductRepository
        ↓
useStorefrontProduct()
        ↓
DetailsView
```

А для социальных данных:

```text
reviews / questions
        ↓
read repositories
        ↓
React Query
        ↓
ReviewsView / QuestionsView
```

Это **очень естественное продолжение текущей архитектуры**, а не новая система.

И отдельно: существующий `ProductImage` уже содержит `storageKey + thumbStorageKey`, а seller mapper уже умеет собирать изображения, варианты, цены и inventory. Поэтому твою идею **"главное + 3 маленьких, при нажатии главное меняется местами с маленьким"** можно реализовать чисто на существующих данных — без новых колонок, без новой обработки фотографий и без усложнения загрузчика.

## Мой предлагаемый порядок работы дальше

Я бы **пока не давал OpenCode/AI кодить весь Product Detail одним промптом**.

Сначала зафиксировал бы отдельный документ:

```text
docs/14_SHOPPIS_PRODUCT_DETAIL_IMPLEMENTATION_PLAN.md
```

в котором будут:

1. **Product Detail UX specification**
2. **точная структура экранов**
3. **route tree**
4. **read-model contracts**
5. **SQL/RPC contract**
6. **review/question data contract**
7. **ProductGroup/related logic**
8. **gallery state machine**
9. **variant/price/inventory state machine**
10. **cart integration**
11. **animation architecture**
12. **loading/error/empty states**
13. **точный список файлов, которые меняем**
14. **точный список новых файлов**
15. **порядок миграций**
16. **порядок реализации по маленьким этапам**
17. **unit/integration/UI tests**
18. **ручной QA checklist**
19. **Definition of Done**

И уже **из него делать последовательные промпты для AI-кодера: один этап → build/typecheck/test → ручная проверка → следующий этап**.

Именно так я бы сейчас и пошёл. Потому что после аудита видно, что Product Detail — это уже не "сделать один экран", а первая полноценная buyer feature, которая одновременно связывает **read model + variants + inventory + images + cart + favorites + reviews + questions + ProductGroup + routing**. Если сейчас сразу дать AI задачу "сделай карточку", он почти наверняка начнёт смешивать эти слои. А у нас уже достаточно хорошая архитектура, чтобы этого не допустить.
