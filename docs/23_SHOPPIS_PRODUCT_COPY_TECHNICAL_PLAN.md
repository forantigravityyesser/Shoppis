## 0. Главный принцип

```text
Создание/редактирование товара   = существующее, не трогаем по смыслу
Копия                            = локальный черновик поверх текущего состояния формы
Сохранение                       = существующий сценарий create (новая карточка) / update (существующая)
Инвентарь                        = источник истины по остаткам (остатки НЕ копируются)
Storage                          = фото НЕ копируются, копия стартует с пустыми фото
```

Три инварианта:

1. **Форма источника — единственный источник копирования.** Копируется **актуальное** (в т.ч.
   несохранённое) состояние активной формы, а не запись из БД. Для режима редактирования —
   поля формы, а не перечитывание исходного товара «специально для копии».
2. **Копия — это режим `create`.** Она не наследует ID исходного товара и никогда не идёт в
   серверный сценарий обновления. Создание копии **не отправляет запрос в БД** (это локальная операция).
3. **Сброс, а не перенос:** фото, storage keys, локальные preview, складские остатки, `held_quantity`,
   резервы, история/отзывы/вопросы, ID товара и вариантов — **не переносятся**.

### 0.1 Четыре обязательных технических условия (🔒)

Закреплены дополнительно к ответам на вопросы; проверяются в приёмке (§16):

1. **Отдельный режим каждого черновика.** Исходная карточка остаётся в режиме **edit** со своим
   `productId`; новая копия стартует в режиме **create**. После первого успешного сохранения копия
   получает собственный `productId`, и последующие сохранения **обновляют именно её**.
2. **Никакого переноса идентификаторов и складских данных.** При клонировании удаляются `Product.id`
   и `Variant.id`; остатки сбрасываются; изображения не копируются. История заказов, резервы, отзывы
   и прочие связанные сущности остаются привязанными к исходному товару.
3. **Защита от повторного создания.** После успешного создания черновик переводится в состояние
   «сохранён» с полученным ID; повторный клик ведёт к **update**, а не к повторному create. При
   **неопределённом** результате (обрыв соединения после отправки) — не повторять create слепо;
   опираться на существующие возможности API и предусмотреть защиту от дублирования (§10.3).
4. **Изоляция черновиков.** Ошибка валидации/сохранения одной копии не сбрасывает другие; переключение
   не теряет несохранённые поля; удаление одной не меняет значения остальных.

## 1. Метод и легенда

### 1.1 Как мы работаем (весь этап)

1. **Один этап за раз** (`PC-00…PC-08`). Между этапами: `npm run typecheck` → `npm run lint` →
   `npm run test` → `npm run build` → ручная сверка (`LOCAL`). Backend-миграций для первой версии
   **не ожидается**; если появятся — дополнительно `npm run migrations:check`.
2. **Двойная среда проверки** (`00` README): `LOCAL VERIFIED` (браузер/локальный контур) +
   `TELEGRAM VERIFIED` (Mini App на dev-окружении). Глобальный этап не закрывается без обоих.
3. **Слоистость:** `View → Hook → Application → Repository/RPC/Edge`. Presentation **не** импортирует
   infrastructure. Доменные правила (цена/скидка/остаток/валидация) не переносятся в компоненты.
4. **Переиспользование, не дублирование.** Не создаём второй калькулятор цены, вторую модель
   варианта, второе поле остатка, вторую валидацию публикации. Используем существующие:
   `toCatalogFields`, `validateProduct`, `validateVariantsForPublish`, `saveProduct`,
   `ProductForm`, `detailToFormValues`, `uploadCatalogImages`.
5. **Минимальность изменений.** Новая функция добавляется **поверх** действующих механизмов;
   существующее поведение форм `create`/`edit` сохраняется.
6. **Порядок качества:** `correct → beautiful → polished`.

### 2.4 Серверный путь создания (атомарность) и режим create vs update

- `useInventoryActions.ts:67-81` — `createProduct` → `NewProductInput` → `saveProduct(input)` (без `id`);
  `updateProduct` → `saveProduct({ id, ...patch })`.
- `product-slice.ts:99-150` — `saveProduct` **сам выбирает create или update по наличию `id`**
  (`'id' in input`), вызывает `validateProduct`, затем `productRepository` и `fetchCatalog`.
  ⚠️ Именно это и есть точка подмены режима: если в create-запись просочится `id` исходного товара,
  копия уйдёт в **update** исходного. Это критический риск (§2.9 R4).
- `product-repository.ts:262-319` — `addProduct`: при `token` → edge `catalog-actions`
  (action `product-create`); иначе (dev/anon, `token === null`) — **прямые SDK-инсёрты**.
- `catalog-api.ts:62-79` → `catalog-actions.js:43-52` → rpc `product_create_atomic`.
- `migrations/0011_catalog_atomic.sql:32-162` — `product_create_atomic` **атомарно** создаёт
  `products` + `product_images` + `product_attributes` + `product_link_attributes` + `variants`
  + `inventory` (остатки строятся из payload; `held_quantity = 0`, строка 155-156).

**Вывод по атомарности (вопрос ТЗ §11 «частичное сохранение»):** для авторизованного продавца
(prod-путь, `token != null`) создание **транзакционно** — частичного товара/вариантов/остатков не будет.
Dev/anon-путь (`token === null`) многошаговый и неатомарный — это **существующее** ограничение
инфраструктуры, не создаваемое этой задачей.

### 2.6 Фотографии

- В форме фото — `InventoryImageItem { url, thumbUrl }` (`inventory-view.ts:6-9`), где `url` фактически
  **storage key** полного файла, `thumbUrl` — ключ миниатюры.
- Загрузка: `image-service.ts:14-33` (`uploadCatalogImages`, параллелизм 2, при сбое — best-effort
  удаление «осиротевших» файлов) → `image-upload.ts:22-29` (full 1000×1250 + thumb 512×640).
- В persistence фото уезжают как `{ storageKey: image.url, thumbStorageKey: image.thumbUrl }`
  (`product-mapping.ts:60-63`).
- Редактирование уже в БД удаляет откреплённые файлы из Storage (best-effort) —
  `product-slice.ts:119-133`; удаление товара — `product-slice.ts:213-216`.

**Следствие:** сброс фото для копии = `images: []` (не «скрыть» картинку в UI, а именно **не передавать
ключи**). Никакого повторного использования `storageKey` исходного товара. ✅ соответствует §7 ТЗ.

### 2.7 Категории

- Список категорий формы приходит из `useInventoryHome` (`CreateProductView.tsx:17`,
  `EditProductView.tsx:14`), который собирает **все** категории магазина + системную «Без категории»
  (`useInventory.ts:106,126-127`).
- `CategoryStatus` существует (`domain/models/category.ts:2`), но в опциях формы фильтр по статусу
  **не применяется** — это существующее поведение. При копировании **нельзя** добавлять собственный
  обход валидации категории; копия получает ту же ссылку `categoryId`, что и источник.
- «Без категории» — системная `UNCATEGORIZED_ID` (`domain/constants/categories.ts:1`), хранится как
  `category_id = null` (`product-mapping.ts:27-30`).

## 4. Остатки и варианты

### 4.1 Структура вариантов

Копия получает **ту же структуру и порядок вариантов** (S/M/L и т.п.), но **без** складских остатков
исходного товара. Структура — из текущего состояния формы (§2.2), а не из БД.

### 4.2 Обязательное заполнение остатков 🔒 (решение Q1)

**Факт:** форма не поддерживает «пустое количество»: `emptyVariant()` = `'0'`, `buildPayload` коэрсит в
число, сервер `greatest(0, ...)`. Полноценное представление «не задано» в текущей модели невозможно без
изменения типа (`VariantForm.quantity: string`) и/или сервера.

**Решение (принято):** третье состояние остатка **не вводим**.

- У копии все количества **обнуляются** (`quantity = '0'`); остаток источника **не** наследуется.
- В интерфейсе поле допускается визуально оставить пустым (если это соответствует существующему UX), но
  при преобразовании данных значение **однозначно `0`**.
- Публикация проходит **существующую** `validateVariantsForPublish` (`variant-form.ts:148-163`) и
  `validateProduct` (`product-rules.ts:58-74`); отдельная «упрощённая» валидация для копий **не вводится**.
- **`0` не обходит существующую валидацию.** Если по бизнес-правилам для публикации нужно положительное
  количество — товар с нулевым остатком **не** становится доступным сам по себе. Если действующие правила
  допускают публикацию без остатка — используем их, а не придумываем новые «специально для копирования».

> **Не менять доменную модель только ради пустого значения.** «Незадано» при необходимости решается в
> presentation-слое (плейсхолдер/подсказка), а не новой доменной семантикой.

### 4.3 Резервирование

При создании копии: резервы (`held_quantity`) не копируются; доступный остаток источника не меняется;
записи резервирования не создаются; `inventory_reconcile` не вызывается; заказы и снимки не затрагиваются.
Сервер `product_create_atomic` создаёт `inventory` с `held_quantity = 0` (`migrations/0011:155-156`).

### 4.4 Независимость после сохранения

После сохранения: изменение остатка/состава вариантов/архивирование одной карточки **не влияет** на другую
(разные `product_id`/`variant_id`/`inventory.variant_id`).

## 5. Цены и скидки

### 5.1 Что переносим

Для товара и каждой опции — исходные настройки: базовая цена, процент скидки, `priceMode` варианта,
`customOriginalAmountMinor`, `customDiscountPercent`, семантика наследования.

### 5.2 Что не делаем

- Не переносим **вычисленную** цену как источник истины — она считается существующими правилами
  (`currentPriceMinor`/`effectivePrice`, `product-rules.ts:22-56`).
- Не заменяем `custom` базой и наоборот; сохраняем различие «отсутствует / переопределено / наследуется»
  (`null` в наследуемой оси — как в `product-mapping.ts:48-49`).
- Не добавляем новый расчёт цены для копии.

### 5.3 Обязательные проверки

1. Одинаковые исходные настройки → одинаковый результат в копии.
2. Изменение скидки копии не меняет источник.
3. Изменение `custom`-цены одного варианта не меняет другие варианты.
4. Снятие `custom` (возврат к наследованию) в копии не меняет источник.
5. Итог считается существующей логикой; корзина/checkout/снимки заказа — через существующие SQL-функции
   (`0037`/`0043`), без изменений.

## 6. Фотографии и Storage

- Новый черновик стартует с **пустыми** `photos`: основной/дополнительные, списки ключей, локальные
  preview — всё пусто (`images: []`).
- Копирование **не** дублирует `storageKey`, **не** переиспользует URL фото источника, **не** загружает
  фото источника повторно, **не** удаляет/меняет исходные файлы, **не** переносит незавершённую загрузку.
- Фото копии грузятся существующим механизмом (`uploadCatalogImages`).
- При неудачном сохранении копии файлы источника не трогаются. При последующем удалении/замене фото копии
  очистка Storage работает только с файлами копии (существующий `removeFilesByUrl`, `product-slice.ts:119-133`).

> **Уточнение после реализации (2026-10-11): фото несохранённой карточки удаляются из Storage.**
> `ProductForm` по-прежнему грузит фото сразу при выборе (нужно для превью), но `ProductDraftEditor`
> отслеживает «свои» загрузки сессии (в edit-режиме — всё, чего нет среди фото товара из БД) и чистит
> их через `removeCatalogImages` (`image-service.ts`): снятие фото с формы — сразу (`onImageRemove`);
> удаление черновика и выход без сохранения («Выйти») — перед уходом; уход вне штатных кнопок
> (системный Back, жест браузера) — при размонтировании редактора. Успешное сохранение файлы не трогает
> (они уже в БД); фото из БД, как и раньше, удаляются только после успешного `update`/`delete` товара
> (`product-slice.ts`). Ограничение: закрытие/перезагрузку страницы очистить нельзя — асинхронное
> удаление при `beforeunload` ненадёжно, guard лишь предупреждает пользователя.

## 7. Пользовательский интерфейс

### 7.1 Кнопка «+ Создать копию»

Компактное действие в **существующей** форме (не новый большой блок). Требования: не перекрывать поля,
системные элементы Telegram и нижние кнопки формы; не добавлять постоянную навигацию, пока черновиков
несколько нет; без агрессивных анимаций/модалок; использовать существующие UI-компоненты и стили
(`inventory.css`, общий `form-header`, `btn-ghost`/`btn-primary`).

### 7.2 Когда показывать

- Create-форма — когда появились данные, которые имеет смысл копировать (простой предикат, напр.
  непустой `title`; **не** новая бизнес-валидация товара).
- Edit-форма — после загрузки товара и инициализации формы.
- При сохранении/загрузке/блокирующей ошибке — по существующим правилам доступности действий.
- Для **пустой** формы кнопка неактивна.

### 7.3 Создание копии (по нажатию)

1. Снять снимок состояния активной формы. 2. Передать в функцию подготовки копии (§13.1).
3. Получить независимый черновик. 4. Переключить форму на новую карточку. 5. Явно показать режим «новая».
6. Сохранить исходный черновик без изменений. 7. Показать пустые фото. 8. Показать, что остатки нужно задать.

**Запрос в БД при нажатии не отправляется.**

> **Уточнение после реализации (2026-10-10):** успешное сохранение карточки («На витрину» / «В архив»)
> убирает её из списка черновиков — данные уже в БД, локальный черновик больше не нужен
> (`completeDraft`, `useProductDraftSave`). Когда список пустеет, форма уходит: create → `/seller/inventory`,
> edit → карточка товара. При ошибке карточка **остаётся** в списке с пометкой «Ошибка сохранения».

### 7.4 Навигация между черновиками

При появлении 2-го черновика — компактная навигация («Карточка 1 — Исходная», «Карточка 2 — Черновик»).
Элемент показывает: номер/имя, статус, наличие несохранённых изменений, выделение активного. Статусы —
фактические: «Черновик», «Есть изменения», «Сохранена», «Ошибка сохранения». Исходная сохранённая карточка
и несохранённая копия **не** имеют одинакового статуса.

### 7.5 Переключение

При переключении: значения и состояния валидации каждого черновика сохраняются; несохранённые изменения
не сбрасываются; повторная загрузка исходного товара/фото без необходимости не запускается; режим
create/edit других черновиков не меняется; **автосохранения в БД при переключении нет**.

### 7.6 Удаление черновика и предупреждение при выходе 🔒 (решения Q3, Q6)

**Удаление черновика (Q6):**

- Подтверждение — **существующим** механизмом проекта (`OrderConfirm` — `OrderConfirm.tsx:16-52`, или
  паттерн `settings-confirm` — `SellerSettingsView.tsx:79-100`). Новый механизм не создавать.
- Удаление **локального** черновика — это **не** удаление товара из БД: исходный товар и любой уже
  сохранённый товар копии **остаются**. Для удаления товара из БД есть существующие операции
  (архив → удаление, `product_set_status_atomic` / `product_delete_atomic`).
- Подтверждение обязательно для черновика с введёнными данными; для совершенно пустого — по действующему UX.
- Удаление черновика не удаляет исходную карточку и не трогает фото источника; собственные файлы
  черновика, если есть, очищаются существующей логикой; при удалении активного черновика активным
  становится другой; удаление единственного нового черновика оставляет форму в допустимом состоянии.

> **Уточнение после реализации (2026-10-10):** удаление реализовано в `ProductDraftEditor` — кнопка «×»
> на черновике (`done` через `remove`/`canRemoveDraft`, модель — `product-draft-session`). Подтверждение —
> локальным блоком `.draft-exit-confirm` в стиле формы (для заполненного черновика); пустой удаляется без
> подтверждения. Кнопка показывается только при `canRemoveDraft(draft)` и наличии ≥2 карточек — так форма
> никогда не остаётся пустой (последнюю карточку удалять нельзя; для выхода — «Назад»). Удаление копии **не**
> трогает товар в БД (при необходимости — архивирование/удаление товара отдельными операциями).

**Предупреждение при выходе (Q3) — минимальное, но полноценное.** Два уровня защиты, **без создания
второго механизма навигации**:

1. **Закрытие/перезагрузка страницы** — `beforeunload`, когда поддерживается.
2. **Внутренний уход со страницы/закрытие формы** — через существующий механизм навигации:
   `BackButton.onClick` (`BackButton.tsx:17,30-33`) в формах создания/редактирования (сейчас там «сырая»
   кнопка `navigate(-1)` — `CreateProductView.tsx:23-30`, `EditProductView.tsx:21-28`).

Предупреждать **только** при наличии несохранённых изменений (не просто из-за нескольких открытых
черновиков), учитывая **все** черновики с изменениями, включая копии и ошибки сохранения. Поведение
системного Back в Telegram Mini App — **проверить по факту** в текущей реализации; не обещать единое
поведение во всех версиях. Не утверждать, что данные сохранены, если они только в памяти.

## 8. Управление состоянием формы

### 8.1 Модель черновика (логическая)

Для каждой карточки различать: `localId` черновика; `mode: 'create' | 'edit'`; `productId?` (только
edit); значения формы (`ProductFormValues`); состояния загрузки фото; статус сохранения; флаг
«есть несохранённые изменения»; ошибку последней операции. Не обязательно новый сложный тип — но
концептуально и технически состояния и идентификаторы **разделены**.

### 8.2 Локальный идентификатор 🔒 (решение Q4)

Стабильный `localId` в рамках сессии (не `productId`). Не использовать порядковый номер/индекс массива
как единственный идентификатор (после удаления нумерация сдвигается, и состояние может попасть не в ту
карточку). Нужен для переключения, адресации асинхронных результатов, статуса, удаления.

**Решение (принято):** `crypto.randomUUID()`; для окружений без него — согласованный с проектом fallback
(без добавления сторонней библиотеки). `localId` — **только клиентский** идентификатор черновика.

### 8.3 Режим create/edit

- **Существующий товар:** реальный `productId`, идёт через `update`.
- **Новая копия:** `localId` без `productId`; сохранение — через **create**; после успеха (см. §13.5) к
  черновику привязывается новый `productId`, статус меняется, повторное сохранение **не создаёт второй товар**.
- **ID привязывается только после подтверждённого успеха.** При ошибке черновик **не** притворяется
  сохранённым (см. §0.1 п.1 и §10.3).

### 8.4 Независимость вложенных данных

Поверхностное копирование запрещено. Глубокая независимость: `attributes`, `variants` (и их поля),
ценовые переопределения, вложенные настройки, массивы изображений, локальные состояния загрузки.
Копирование — через **отдельную функцию**, явно определяющую что переносить/сбрасывать.

> Не использовать `JSON.parse(JSON.stringify(...))` как основной механизм без проверки типов/семантики.
> Использовать явные конструкторы (`emptyVariant`, `variantFromBase`, маппинг полей).

## 9. Ограничение количества карточек

Максимум **6** карточек в одной сессии формы (1 исходная + до 5 копий). Требования:

- Проверка **до** создания черновика; при достижении лимита кнопка недоступна/заменена пояснением.
- Уже созданные черновики продолжают редактироваться/сохраняться; сохранение одной не публикует другие.
- Лимит не блокирует обычное создание товара вне сессии черновиков.
- Проверка — в **управляющей логике** сессии, а не только скрытием кнопки.
- Без серверных лимитов/таблиц/настроек. 🔒 `R8`: константу держать в application-слое сессии, **не** в
  `domain/constants/limits.ts` (там только размерности товара/корзины).

## 10. Сохранение карточек

### 10.1 Независимое сохранение

Каждая карточка сохраняется отдельно; успех/ошибка одной не откатывает другие; ошибочная остаётся
черновиком с понятной ошибкой; пользователь исправляет и сохраняет отдельно.

### 10.2 Валидация

Каждая карточка проходит **существующую** валидацию (`validateProduct`, `validateVariantsForPublish`).
Не создавать упрощённую схему для копий. Ошибки отображаются **в конкретной** карточке; при переключении
ошибка одной не показывается как ошибка другой.

### 10.3 Защита от повторной отправки

На время сохранения: блокировать повторную отправку **той же** карточки; показать существующий индикатор;
сохранить содержимое; корректно обработать ошибку; не блокировать остальные черновики без необходимости.
Повтор после ошибки не должен дублировать товар/варианты/остатки.

**Неопределённый результат (обрыв после отправки) — 🔒 обязательное условие №3.** После **успешного**
создания черновик переводится в состояние «сохранён» с полученным `productId`, и повторный клик идёт в
**update**. Если результат **неопределён**, нельзя слепо повторять create: опираться на существующие
возможности сервера и/или трактовать неопределённый ответ как «не сохранять повторно без проверки».
Отдельного идемпотентного ключа для `product-create` (`0011`) сейчас нет — если понадобится, это
оформляется как минимальное изменение на этапе PC-00/PC-04 с обоснованием конкретного риска (без новой
инфраструктуры «ради копии»).

### 10.4 Публикация и архивирование

Использовать существующие сценарии статуса (`ACTIVE`/`ARCHIVED`, `product_set_status_atomic`). Пользователь
сам решает по каждой карточке. **Нельзя:** авто-публиковать все копии; переносить статус источника;
архивировать источник при архивации копии; менять поведение существующей публикации.

## 13. Целевая архитектура и распределение ответственности

> Это распределение **ответственности**, а не предписание конкретных имён файлов. Итоговые пути — после
> подтверждения Stage 0.

### 13.1 Функция подготовки копии

Небольшая **чистая** функция (application/rules), которая: принимает значения формы; копирует разрешённые
поля; создаёт независимые вложенные объекты; сбрасывает фото и состояния загрузки; исключает `id` товара
и вариантов; сбрасывает остатки; возвращает корректный черновик **без побочных эффектов**. Не обращается
к БД/Storage, не сохраняет, не пересчитывает цены альтернативно.

### 13.2 Управление коллекцией черновиков

Небольшая управляющая логика (application-слой / хук сессии): добавление черновика, проверка лимита (6),
переключение, удаление локального черновика, обновление состояния одной карточки, активный `localId`,
сохранение независимости остальных. **Не** помещать в компонент формы.

**🔒 Решение Q5.** Сессия черновиков — **временное состояние интерфейса**, а не server-state и не
глобальное состояние приложения. Поэтому: чистая логика коллекции — в application **без зависимости от
React**; React-хук/адаптер связывает её с UI. **Новый Zustand-срез по умолчанию не создаём**; он
оправдан только если аудит покажет, что сессией должны совместно управлять независимые экраны
(на текущий момент таких требований нет). React-хук не помещаем в domain.

### 13.3 Существующая форма `ProductForm`

Продолжает отвечать за отображение полей, изменение значений, существующую валидацию, работу с опциями,
ценой/скидкой, фото, выбор статуса и вызов существующего сценария сохранения. Минимально разделить
«отображение» и «данные», чтобы одна форма работала с **выбранным** черновиком (сделать контролируемой
или перемонтируемой по `localId`). **Не** создавать вторую полноценную форму с копией логики.

### 13.4 Application-слой сохранения

Использовать существующие `createProduct`/`updateProduct` (`useInventoryActions`). Для копии — **create**;
никогда не передавать `id` исходного товара и не использовать update для копии. Сохранение остаётся
существующим (Zustand-слайс → repository → RPC).

### 13.5 Возврат `productId` из create-цепочки 🔒 (решение Q2 = вариант A, обязателен)

Чтобы выполнить §0.1 п.1/§8.3/§10.3 (повторное сохранение не создаёт второй товар), приложение должно
знать `productId` созданной копии. **Принято: вариант A** — расширить сигнатуры **только необходимых
слоёв**:

- `product_create_atomic` уже возвращает `productId` (`migrations/0011:160`);
- пробросить его: `catalog-api.createProduct` → `productRepository.addProduct` →
  `product-slice.saveProduct` (вернуть `{ productId }` вместо `void`) → application-контроллер черновиков;
- существующий стиль обработки ошибок сохраняется.

**Вариант B (сопоставление по названию/времени/порядку) отклонён** как ненадёжный (параллельные операции,
повторные запросы).

**Условие:** `productId` присваивается конкретному черновику **только после подтверждённого успешного
создания**; при ошибке черновик не считается сохранённым. Изменение сигнатур — **единственное**
оправданное касание application/infrastructure; домен и правила не затрагиваются.

### 13.6 Infrastructure и БД

Сохранять через действующие репозитории/адаптеры. Копия получает новый `product_id`, новые `variant_id`,
собственные `inventory`-записи, собственные ссылки на фото, допустимые статусы. **Схему БД не менять** —
`product_create_atomic` уже покрывает требования (новые id, `held_quantity = 0`, атомарность).

## Итоговый принцип

Мы **не создаём новую систему товаров**. Мы добавляем удобный способ подготовить несколько независимых
форм на основе уже существующих данных.

**Копирование — локальное преобразование данных формы. Сохранение — отдельная операция создания или
обновления конкретного товара. Инвентарь — источник истины по остаткам. Фотографии — самостоятельные
файлы. После копирования никаких связей между карточками нет.**

Реализация должна быть минимальной по объёму изменений, но полной по защите данных, тестам и
регрессионным сценариям. Если текущая архитектура не позволяет безопасно реализовать пункт без
дополнительных изменений, это обосновывается конкретным участком кода и предлагается минимальное решение,
а не обход существующих правил.
