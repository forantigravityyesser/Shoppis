## 1. Назначение

Этот документ — source of truth для реконструкции области Seller Inventory.

Текущая реализация Inventory функционально substantial и имеет хороший архитектурный фундамент, но presentation-слой накопил слишком много ответственности, а также несколько UX- и mutation-lifecycle проблем.

Цель — **не** переписать Inventory с нуля.

Цель:

1. Сохранить существующую Onion Architecture.
2. Сохранить существующие границы domain/application/infrastructure.
3. Исправить известные ошибки корректности и UX.
4. Разделить Inventory на чёткие функциональные секции.
5. Сделать Products и Categories масштабируемыми по мере роста каталога.
6. Защитить все пользовательские мутации от дублирующей отправки.
7. Сделать наследование вариантов явным, а не неявным.
8. Держать документацию синхронизированной с фактической реализацией.
9. Добавить регрессионные тесты для критического поведения, вводимого реконструкцией.

## 2. Не-цели

Реализация **не** должна вводить лишнюю сложность.

Не добавлять в рамках этой задачи:

- React Query или другой server-state фреймворк, если конкретная архитектурная проблема не требует этого.
- Drag-and-drop сортировку категорий.
- Массовое редактирование товаров.
- Массовые операции с категориями.
- Продвинутую фильтрацию товаров.
- Пагинацию/виртуализацию, если текущие объёмы данных реально не требуют этого.
- SKU-менеджмент.
- Аналитику.
- Редизайн резервирования инвентаря.
- Новые системы нотификаций.
- Новые backend-абстракции без доказанной необходимости.
- Вторую frontend-архитектуру.
- Второе решение для управления состоянием.
- Несвязанный рефакторинг вне затронутых областей Inventory/Product/Category.

Реализация должна оставаться адекватной текущему MVP, но структурно готовой к будущему росту.

## 3. Архитектурные принципы

### 3.1 Onion Architecture обязательна

Текущее направление слоёв должно сохраниться:

```text
Presentation
    ↓
Application
    ↓
Domain

Infrastructure implements application contracts
```

Presentation не должен напрямую обращаться к:

- InsForge/Supabase-клиентам;
- запросам к БД;
- infrastructure-репозиториям;
- persistence-специфичным DTO.

Presentation работает через application-хуки/экшены/read-модели.

### 3.2 Domain остаётся независимым

Бизнес-правила не должны переезжать в React-компоненты только потому, что там их удобно реализовать.

Если правило описывает бизнес-поведение, а не визуальное, оно принадлежит:

- Domain, или
- Application/use-case слою.

Примеры:

- эффективная цена варианта;
- семантика наследования/custom-цены;
- порядок категорий;
- валидация, необходимая для публикации.

Примеры presentation-логики:

- открытие sheet;
- выбранная секция Inventory;
- loading spinner;
- фокус инпута;
- disabled-состояние кнопки.

### 3.3 Не создавать God component

`InventoryView` должен остаться composition/root-компонентом.

Он не должен отвечать за:

- бизнес-правила товара;
- реализацию мутаций категорий;
- расчёт цены вариантов;
- сложный рендеринг списков;
- всё состояние sheets;
- всю валидацию;
- всю навигационную логику.

Предпочитать сфокусированные компоненты и хуки/билдеры read-моделей.

## 4. Архитектурные активы, которые сохраняем

В проекте уже есть несколько хороших архитектурных решений.

Не заменять их без необходимости.

Сохраняем:

- `CategorySlice`;
- абстракцию category repository;
- application-контракты;
- подход inventory read-model;
- application-хуки product/category;
- независимый route shell `ProductView`;
- независимый route shell `CategoryView`;
- оптимистичный reorder категорий с rollback;
- существующий механизм реордера категорий;
- текущие границы слоёв Onion.

В частности, существующая команда реордера:

```ts
reorderCategory(id, position)
```

должна остаться отдельной семантической операцией.

Не превращать порядок категорий в произвольное обновление поля только потому, что UI показывает текущую позицию.

## 5. Информационная архитектура Inventory

Seller Inventory должен быть реконструирован вокруг двух основных секций:

```text
Inventory
├── Товары
└── Категории
```

Секция по умолчанию:

```text
Товары
```

потому что товары — основной объект инвентаря.

Компактный переключатель секций должен отображаться рядом с заголовком Inventory:

```text
[ Товары ] [ Категории ]
```

Переключатель — это UI-состояние, ему не нужно становиться глобальным application-состоянием.

---

## 6. Inventory — секция «Товары»

### 6.1 Назначение

Секция «Товары» — основное рабочее пространство для управления всеми товарами продавца.

Она обязана предоставлять:

- все товары;
- поиск по товарам;
- статус товара;
- информацию о категории;
- информацию об остатках/инвентаре, где она уже доступна;
- навигацию к товару;
- создание товара.

### 6.2 Список товаров

Секция должна использовать масштабируемый список, а не визуально перегруженную сетку карточек.

Рекомендуемая концептуальная структура:

```text
ProductsSection
├── ProductSearch
├── ProductList
│   └── ProductRow
└── EmptyState
```

Каждая строка товара должна давать достаточно информации для быстрого узнавания, не превращаясь в мини-страницу товара.

Как минимум:

- изображение товара;
- название товара;
- категория;
- релевантная информация об остатках;
- цена;
- состояние active/archived;
- навигация к деталям товара.

Точная визуальная композиция может следовать существующей дизайн-системе Shoppis.

### 6.3 Поиск

Поиск должен работать по уже доступной inventory product read model.

Не вводить отдельную backend-систему поиска в рамках этой области, если текущие объёмы данных не доказывают, что клиентской фильтрации недостаточно.

Поиск должен:

- быть отзывчивым;
- не мутировать domain-состояние;
- не храниться глобально;
- иметь чёткое состояние «ничего не найдено».

---

## 7. Inventory — секция «Категории»

### 7.1 Принципиальное изменение

Существующая сетка категорий должна быть удалена/заменена.

**Не** использовать 50/50 двухкарточный layout для управления категориями.

Предыдущий layout создаёт серьёзную responsive-проблему, когда названия категорий, информация о порядке и счётчики архивных товаров становятся длинными.

Категории должны отображаться **полноширинными строками**.

### 7.2 Список категорий

Рекомендуемая структура:

```text
CategoriesSection
├── CategoryList
│   └── CategoryRow
│       ├── CategoryHeader
│       ├── CategoryMeta
│       ├── CategoryPreviewRow
│       └── CategoryActions
└── EmptyState
```

Каждая категория занимает доступную ширину.

Строка категории может содержать:

- изображение категории;
- название категории;
- порядок категории;
- состояние active/archived;
- общее число товаров;
- число архивных товаров, где релевантно;
- компактное превью товаров;
- действие редактирования;
- навигацию в `CategoryView`.

### 7.3 Требование responsive

Строка категории не должна полагаться на фиксированное горизонтальное расположение, где все метаданные обязаны поместиться в одну строку.

Длинные названия категорий должны переноситься естественно.

Layout должен оставаться валидным, когда:

- название категории длинное;
- счётчики товаров большие;
- отображается архивный счётчик;
- отображается позиция порядка;
- видны кнопки действий;
- ширина viewport маленькая.

Горизонтальный overflow страницы недопустим.

Это требование корректности, а не только визуальное предпочтение.

---

## 8. Навигация по категориям

Клик по категории должен открывать `CategoryView`.

`CategoryView` должен содержать:

- идентичность категории;
- список товаров категории;
- навигацию к товарам;
- действие «добавить товар»;
- действие редактирования категории в области справа сверху.

CategoryView не должен дублировать бизнес-логику категории, которая уже принадлежит application/domain-слоям.

---

## 9. Редактирование категории

UI редактирования категории должен показывать текущий порядок отображения на витрине.

Однако **не превращать `sortOrder` в обычное редактируемое текстовое поле**.

Существующая семантическая команда должна сохраниться:

```ts
reorderCategory(id, position)
```

Рекомендуемый UX:

```text
Порядок на витрине

3 из 8

[ Изменить порядок ]
```

Клик по «Изменить порядок» открывает существующий механизм реордера.

Пользователь не должен вводить произвольные значения вида:

```text
999
-3
```

UI реордера отвечает за валидные позиции.

---

## 10. Mutation lifecycle реордера категории

Текущее оптимистичное поведение реордера хорошее и должно сохраниться.

Обязательный lifecycle:

```text
IDLE
  ↓
SUBMITTING
  ↓
SUCCESS
```

или:

```text
IDLE
  ↓
SUBMITTING
  ↓
ERROR
```

Во время отправки:

- релевантные контролы disabled;
- дублирующие запросы реордера предотвращены;
- показан видимый feedback сохранения;
- sheet не закрывается до успешного завершения.

При успехе:

- закрыть UI реордера;
- сохранить обновлённый порядок.

При ошибке:

- откатить оптимистичное состояние;
- оставить UI реордера доступным;
- показать действенную ошибку;
- позволить повторить.

Не использовать fire-and-forget мутацию с немедленным закрытием sheet.

Плохо:

```ts
void reorderCategory(...)
onClose()
```

Предпочтительное концептуальное поведение:

```ts
await reorderCategory(...)
onClose()
```

с корректной обработкой ошибок и loading-состоянием.

---

## 11. Mutation lifecycle редактирования категории

Тот же mutation lifecycle должен применяться к редактированию категории.

Обязательное поведение:

```text
Editing
  ↓
Submit
  ↓
Saving...
  ↓
Success → close
```

или:

```text
Saving...
  ↓
Error → remain open + show error
```

Пользователь никогда не должен терять форму из-за того, что приложение молча упало.

## 12. Создание/публикация товара

### 12.1 Известная проблема

Форма создания/редактирования товара сейчас позволяет нажать:

```text
На витрину
```

пока асинхронная операция ещё выполняется.

Если UI выглядит зависшим, продавец может нажать повторно и создать дубликаты товаров.

Это должно быть исправлено.

### 12.2 Обязательное submit-состояние

`ProductForm` должен иметь выделенное состояние отправки.

Концептуально:

```ts
const [submitting, setSubmitting] = useState(false);
```

Отправка должна быть защищена guard'ом.

Концептуально:

```ts
if (submitting) return;

setSubmitting(true);

try {
  await onSubmit(payload);
} finally {
  setSubmitting(false);
}
```

Точная реализация может отличаться, но поведение обязательно.

### 12.3 Поведение UI

Во время отправки:

- кнопка публикации disabled;
- другие конфликтующие действия отправки disabled;
- кнопка сообщает о прогрессе;
- дублирующие клики ничего не делают;
- форма не производит дублирующих запросов.

Например:

```text
На витрину
```

становится:

```text
Публикация...
```

или эквивалентный визуальный feedback.

### 12.4 Поведение при ошибке

Если публикация упала:

- форма остаётся открытой;
- введённые данные сохранены;
- submitting-состояние сбрасывается;
- показана понятная ошибка;
- продавец может повторить.

Не глотать ошибку молча.

## 13. Проброс ошибок мутаций

Пользовательские мутации не должны молча глотать ошибки.

Application-экшены должны возвращать rejected Promise или явный типизированный failure, который Presentation может обработать.

Избегать архитектуры, где application-экшен делает:

```ts
try {
   ...
} catch (error) {
   console.error(error);
}
```

и с точки зрения UI завершается успешно.

Presentation должен знать, что операция упала.

Правило применяется к:

- созданию товара;
- обновлению товара;
- публикации товара;
- архивации товара;
- созданию категории;
- обновлению категории;
- удалению категории;
- архивации категории;
- реордеру категории;
- релевантным inventory-мутациям.

## 14. Наследование вариантов товара

### 14.1 Известный баг

Текущее наследование цены варианта выводится из текущего значения инпута.

Концептуально текущая логика ведёт себя как:

```ts
customPrice =
  index !== 0 &&
  value.trim() !== '' &&
  value !== basePrice;
```

Это создаёт критический UX-баг.

Пример:

```text
Базовая цена: 1900

Вариант 1: 1900
Вариант 2: унаследовано 1900
Вариант 3: унаследовано 1900
```

Продавец начинает вводить:

```text
2200
```

но при удалении существующего значения инпут становится пустым.

Приложение интерпретирует:

```text
empty
```

как:

```text
не custom
```

и немедленно восстанавливает:

```text
1900
```

Продавец не может естественно очистить поле и ввести новое значение.

---

## 15. Обязательная модель наследования

Наследование должно быть представлено явно.

Не выводить наследование из строкового равенства или пустых строк.

Рекомендуемая модель формы:

```ts
interface VariantForm {
  id?: string;
  name: string;
  value: string;
  quantity: string;

  price: string;
  discount: string;

  priceMode: 'INHERITED' | 'CUSTOM';
  discountMode: 'INHERITED' | 'CUSTOM';
}
```

Точные имена могут отличаться, но семантическое различие обязано существовать.

Для базового варианта наследование неприменимо, либо базовые значения всегда являются source-значениями.

---

## 16. Поведение цены варианта

Для небазового варианта:

### Начальное состояние

```text
priceMode = INHERITED
price = базовая эффективная цена
```

### Пользователь начинает редактировать

Приложение обязано переключиться в:

```text
priceMode = CUSTOM
```

Поле после этого может содержать:

```text
2200
```

или временно:

```text
""
```

Пустая строка — валидное **состояние редактирования формы**, но не валидная публикуемая цена.

---

## 17. Очистка custom-значения

Это поведение обязательно:

```text
База = 1900
Вариант = inherited

Пользователь вводит 2200
→ CUSTOM / 2200

Пользователь удаляет всё
→ CUSTOM / ""

Пользователь вводит 2
→ CUSTOM / 2
```

Приложение **не должно** восстанавливать:

```text
1900
```

только потому, что инпут временно стал пустым.

---

## 18. Явный возврат к наследованию

Возврат к наследованию должен быть явным действием пользователя.

Например:

```text
[ Своя цена ]
[ Использовать цену товара ]
```

или эквивалентный UI.

Не использовать:

```text
пустой инпут = наследовать
```

потому что это смешивает состояние редактирования и бизнес-состояние.

---

## 19. Изменение базовой цены

Пример:

```text
Базовая цена = 1900

Вариант A = inherited
Вариант B = custom 2200
```

Продавец меняет базовую цену:

```text
2000
```

Ожидаемо:

```text
Вариант A → 2000
Вариант B → 2200
```

Только inherited-варианты следуют за базой.

Custom-варианты остаются независимыми.

## 20. Наследование скидки варианта

Применить тот же архитектурный принцип к скидке, если наследование скидки сейчас существует.

Не реализовывать одну модель наследования для цены и другую неявную модель для скидки.

Обе должны различать:

```text
INHERITED
```

и:

```text
CUSTOM
```

и временное состояние формы:

```text
""
```

## 21. Эффективные значения варианта

Presentation-слой не должен решать бизнес-семантику вида:

```text
effectivePrice = custom ? customPrice : basePrice
```

Создать или переиспользовать application/domain-правило для эффективных значений варианта.

UI должен потреблять эффективное значение.

Это особенно важно для валидации публикации.

---

## 22. Валидация публикации

Текущая валидация не должна проверять только сырой инпут варианта.

Например, логика вида:

```ts
parsePriceMinor(v.price) > 0
```

недостаточна, когда существует явное наследование.

Валидация должна работать с эффективным бизнес-состоянием.

Правила должны включать:

- значение варианта валидно;
- количество валидно;
- эффективная цена валидна;
- обязательные данные товара присутствуют;
- custom-цена не может быть пустой, когда вариант помечен `CUSTOM`.

Пример:

```text
priceMode = CUSTOM
price = ""
```

должен проваливать публикацию с понятным сообщением валидации.

Он не должен молча откатываться к базовой цене.

## 25. Навигация Seller Product View

Целевая навигация seller-карточки:

```text
Карточка
Отзывы   [N]
Вопросы  [M]
Витрина
```

- `Карточка`, `Витрина` — секции управления товаром.
- `Отзывы` и `Вопросы` — per-product секции; остаются по правке заказчика (INV-R-08 переопределён).
- Индикатор `[N]` на «Отзывы» — число **непросмотренных** отзывов. При заходе на вкладку
  отзывы помечаются просмотренными, бейдж гаснет.
- Индикатор `[M]` на «Вопросы» — число **вопросов без ответа**. «Просмотренным» считается
  отвеченный вопрос; после ответа бейдж уменьшается.

В `ProductOverview` действия/ссылки на отзывы и вопросы **удалены** (`INV-R-09`); счётчики
показываются только бейджами навигации.

Технически:
- `ProductView` читает счётчики через `useSellerProductReviews`/`useSellerProductQuestions`
  (React Query, тот же кэш, что у вкладок) и считает непросмотренные/неотвеченные.
- Просмотренные отзывы хранит `application/hooks/useSellerSocialSeen.ts` (localStorage per product;
  это UI-состояние продавца, не домен). `ProductReviewsView` помечает список через
  `useMarkReviewsSeen`.

Domain- и application-функциональность отзывов/вопросов не удаляется.

## 33. Стандарт mutation UX

Все пользовательские асинхронные мутации в этой области должны следовать:

```text
IDLE
  ↓
SUBMITTING
  ↓
SUCCESS
```

или:

```text
IDLE
  ↓
SUBMITTING
  ↓
ERROR
```

Правила:

1. Дизейблить триггерящее действие во время отправки.
2. Предотвращать дублирующие запросы.
3. Показывать прогресс.
4. Сохранять состояние формы при ошибке.
5. Позволять повтор.
6. Закрывать modal/sheet только после успешного завершения.
7. Не глотать application-ошибки молча.

Это становится переиспользуемой конвенцией проекта для seller-мутаций.

## 34. Требования DRY

Не дублировать:

- парсинг цены;
- парсинг скидки;
- расчёт эффективной цены;
- семантику наследования вариантов;
- правила порядка категорий;
- логику mutation lifecycle;
- повторяющиеся паттерны обработки ошибок, если существующая абстракция проекта может быть переиспользована.

Однако не создавать искусственные абстракции только чтобы убрать две визуально похожие строки.

DRY должен сохранять читаемость.

- навигация;

### Infrastructure

Не вносить persistence-детали в Presentation.

## 36. Порядок категорий как источник истины

Текущая реализация поддерживает ручной порядок категорий.

Следовательно:

```text
sortOrder
```

является частью текущего storefront-поведения.

Репозиторий/application-команда:

```text
reorderCategory(id, position)
```

должна остаться семантическим источником операции.

Не удалять ручной порядок потому, что старый документ говорит, что порядок не планировался.

Реализация опережает устаревшую документацию.

```text
docs/07_SHOPPIS_INVENTORY_UX_SPEC_v0.1.md
```

Это особенно важно, потому что AI-агенты могут использовать старые документы как архитектурные инструкции и случайно зарегрессировать уже реализованную функциональность.

```text
Explicit state
+
Clear responsibilities
+
Stable Onion boundaries
+
Predictable mutations
+
Testable business rules
+
Simple scalable UI
```

вместо краткосрочных shortcuts.

## A.4 Дополнительные находки (вне входящей спеки)

1. **«В архив» без заполненного варианта молча падает.** `validateProduct` требует `originalAmountMinor > 0` независимо от статуса (`product-rules.ts:55-68`, `product-slice.ts:132-138`), а ошибка глотается (`useInventoryActions.ts:149-151`), хотя `docs/06:469` обещает доступность архивации без вариантов. Рекомендуется закрыть в рамках `INV-R-02` (валидация по бизнес-состоянию) и `INV-R-06` (проброс ошибок).
2. **Мёртвый код:** `EmptyInventoryState.tsx` не импортируется ни одним компонентом; `ProductTabEmpty.tsx` не используется. Закрывается в `INV-R-34`.
3. **`AddVariantSheet` — та же болезнь:** `AddVariantSheet.tsx:48-58` вызывает `addVariant(...)` без `await` и сразу `onClose()`; попадает под стандарт mutation UX §33 (в исходной спеке не перечислен, но формально покрыт).
4. **Противоречие `07 §12` и §31 спеки:** `07` утверждает «отдельного пустого экрана на Home нет» (системная «Без категории» существует всегда), а §31 требует осмысленные пустые состояния секций. Синхронизировать в `INV-R-37`.
5. **Публикация на сервере слабее клиента:** `product_create_atomic` не содержит guard `NO_ACTIVE_VARIANT` (есть только в `product_update_atomic`, `0011`), а цена при создании зажимается через `greatest(0, ...)`. Не менять в рамках реконструкции (backend вне scope), но учесть в тестах.

## A.7 Влияние на план

- Утверждения §12–§24 (нет submitting, дубли, наследование из инпута, валидация по raw, fire-and-forget реордер, проглоченные ошибки, Отзывы/Вопросы в ProductView) **подтверждены кодом** — фазы A–C обязательны и не пересматриваются.
